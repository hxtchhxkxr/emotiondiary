# 05. 성능 테스트 개요

## 학습 목표

- 성능 테스트가 필요한 이유를 설명할 수 있다.
- Smoke·Load·Stress·Spike·Soak 테스트의 목적을 구분할 수 있다.
- VU, TPS, 응답 시간, p95, 오류율을 이해하고 해석할 수 있다.
- SLI·SLO·SLA의 차이를 구분할 수 있다.
- 사용자 행동에 가까운 부하 시나리오와 성공 기준을 정할 수 있다.

## 핵심 개념

### 성능 테스트란?

기능 테스트가 “올바른 결과를 반환하는가?”를 묻는다면, 성능 테스트는 다음을 묻는다.

- 얼마나 **빠르게** 응답하는가?
- 초당 얼마나 **많은 요청**을 처리하는가?
- 사용자가 늘어도 얼마나 **안정적으로** 동작하는가?
- 오래 실행했을 때 메모리·커넥션 등이 고갈되지 않는가?
- 어느 부하에서 성능 목표를 위반하거나 시스템이 무너지는가?

결과는 “빠르다” 같은 느낌이 아니라 **응답 시간, TPS, 오류율, CPU, 메모리, DB 커넥션** 같은 숫자로 기록한다.

### 성능 테스트가 필요한 이유

- **사용자 경험**: 늦은 페이지와 API는 사용자 이탈로 이어진다.
- **병목 조기 발견**: 실제 트래픽이 오기 전에 DB·JVM·네트워크의 한계를 찾는다.
- **용량 계획**: 목표 사용자를 감당하려면 얼마의 서버·DB 자원이 필요한지 판단한다.
- **성능 회귀 방지**: 코드 변경 후 기존 대비 응답 시간이 악화됐는지 검증한다.
- **운영 비용 최적화**: 과도한 사양과 부족한 사양 사이에서 근거 있는 선택을 한다.

### 성능 테스트의 종류

| 종류 | 확인하는 것 | 부하 모양 |
| --- | --- | --- |
| Smoke | 스크립트와 핵심 API가 기본적으로 동작하는가? | 1~2 VU, 짧게 |
| Load | 예상한 평상시 부하를 견디는가? | 목표 부하를 일정 시간 유지 |
| Stress | 부하를 늘리면 어디서 한계가 오는가? | 계단식으로 계속 증가 |
| Spike | 순간적인 트래픽 폭증을 견디고 회복하는가? | 급격히 증가 후 감소 |
| Soak | 오래 실행할 때 누수·GC·자원 고갈이 생기는가? | 중간 부하를 수 시간 유지 |
| Breakpoint | 정확히 어느 지점에서 목표를 위반하는가? | 한계까지 증가 |

처음에는 **Smoke → Load → Stress** 순으로 시작하는 것이 좋다. 작은 부하에서 스크립트와 환경을 검증하지 않고 바로 큰 부하를 주면, 애플리케이션 문제와 테스트 설정 문제를 구분하기 어렵다.

### 핵심 지표와 용어

| 용어 | 의미 |
| --- | --- |
| Response Time | 요청을 보낸 뒤 응답을 받는 데 걸린 시간 |
| Latency | 데이터 전달·서버 대기 등으로 생기는 지연. 도구별 정의를 확인해야 함 |
| RPS | 1초에 처리한 HTTP Request 수 |
| TPS | 1초에 처리한 비즈니스 Transaction 수 |
| Concurrent User | 같은 시점에 시스템에 접속해 있는 사용자 |
| Active User | 현재 요출을 보내거나 시나리오를 수행하는 사용자 |
| VU | 부하 도구가 흘내 내는 가상 사용자 |
| Ramp-up | 부하를 목표치까지 점진적으로 올리는 구간 |
| Error Rate | 전체 요청 중 실패로 정의한 요청의 비율 |
| Saturation Point | 부하를 늘려도 처리량은 늘지 않고 대기 시간만 커지는 포화점 |

RPS와 TPS는 종종 비슷한 뜻으로 쓰이지만 엄밀히는 다르다. 일기 작성 하나가 여러 HTTP 요청으로 구성되면 RPS와 비즈니스 TPS가 같지 않을 수 있다. 리포트에서 어떤 의미로 쓴 지표인지 명시해야 한다.

### VU와 TPS는 같지 않다

VU는 동시에 시나리오를 실행하는 가상 사용자의 수이다. TPS는 시스템이 초당 완료한 처리량이다.

같은 100 VU여도 응답 시간과 Think Time에 따라 TPS가 달라진다. 따라서 “100 VU = 100 TPS”라고 계산하면 안 된다.

### p50·p95·p99와 평균

평균은 몇 개의 매우 느린 요청에 의해 쉽게 왜곡된다. 성능 테스트에서는 전체 사용자의 경험 분포를 보기 위해 백분위를 함께 사용한다.

- **p50**: 50%의 요청이 이 시간 이내에 완료된다. 중앙값이다.
- **p95**: 95%의 요청이 이 시간 이내에 완료된다.
- **p99**: 99%의 요청이 이 시간 이내에 완료된다. GC·Slow Query 같은 드문 지연을 보기 좋다.

예를 들어 `p95 = 480ms`는 **100개 요청 중 약 95개가 480ms 이내에 응답했다**는 뜻이다. 나머지 약 5%는 480ms보다 느릴 수 있다.

### SLI·SLO·SLA

| 용어 | 쉽게 말하면 | 예시 |
| --- | --- | --- |
| SLI | 실제로 측정한 값 | 일기 조회 p95 = 420ms |
| SLO | 팀 내부의 성능 목표 | 일기 조회 p95 < 500ms |
| SLA | 고객과 약속한 서비스 수준 | 월간 가용성 99.9% 등 |

목표 수치는 모든 API에 똑같이 적용하지 않는다. BCrypt 비밀번호 검증을 수행하는 로그인 API는 단순 조회 API보다 자연스럽게 느릴 수 있으므로 엔드포인트별로 기준을 정한다.

### TPS와 응답 시간의 관계

부하를 계속 늘리면 보통 다음 순서로 시스템의 상태가 변한다.

1. **가벼운 부하**: VU와 TPS가 함께 늘고 응답 시간은 비슷하다.
2. **포화 접근**: TPS 증가 속도가 느려지고 응답 시간이 증가한다.
3. **포화**: VU를 늘려도 TPS는 늘지 않고 응답 시간만 크게 증가한다.
4. **과부하**: TPS가 오히려 하락하고 타임아웃·5xx·커넥션 거절이 증가한다.

부하가 늘었는데 TPS는 비슷하고 p95만 올랐다면 시스템이 한계에 가까워졌다는 신호다.

### 병목이 발생하는 계층

#### Application·JVM

- 동기화·Lock 경쟁
- 지나친 객체 생성과 GC
- Tomcat Thread Pool 포화
- JPA N+1 쿼리

#### Database

- 인덱스가 없는 Slow Query·Full Table Scan
- Row Lock 경쟁
- HikariCP 커넥션 풀 고갈
- 비효율적인 JOIN·정렬

#### Network·Infrastructure

- 지리적 거리와 네트워크 지연
- DNS·Proxy·Load Balancer 설정
- 대역폭 한계

#### Client·Browser

- 큰 JavaScript 번들과 렌더링 블로킹
- 최적화되지 않은 이미지·캐시

부하 테스트 결과만으로 병목 원인을 확정할 수는 없다. 같은 시각의 JVM·DB·OS 지표와 로그를 함께 봐야 한다. 이 연결이 7단원 Prometheus·Grafana와 8단원 ELK의 목적이다.

### Slow Query 해결 순서

DB 쿼리가 병목으로 의심된다면 추측만으로 인덱스를 추가하지 않는다.

1. `EXPLAIN`으로 실행 계획을 확인한다.
2. 조회·정렬 조건에 맞는 인덱스를 검토한다.
3. 필요한 컬럼만 조회하고 JOIN·서브쿼리를 정리한다.
4. N+1이라면 Fetch Join·EntityGraph·DTO Projection을 검토한다.
5. 실제 부하를 다시 주어 Before/After를 비교한다.

### k6를 사용하는 이유

k6는 JavaScript로 시나리오를 작성하는 CLI 기반 부하 테스트 도구다.

- 스크립트를 Git에 저장하고 리뷰하기 쉽다.
- Docker로 실행하기 쉽다.
- Threshold 실패를 종료 코드로 반환해 CI에 연결할 수 있다.
- Prometheus·Grafana와 연결하기 좋다.

JMeter·nGrinder·Gatling·Locust도 각각 장점이 있다. 이 강의에서는 코드·Git·CI·관측성 흐름을 연결하기 좋은 k6를 사용한다.

## 프로젝트 적용

emotiondiary의 첫 성능 테스트 대상은 사용자의 주요 흐름이다.

```text
회원가입(setup, 최초 1회)
  → 로그인
  → 일기 목록 조회
  → 일기 작성
  → 일기 수정
  → 일기 삭제
```

단일 API만 빠르게 반복하면 실제 사용 패턴과 다른 결과가 나올 수 있다. 로그인, 조회, 쓰기의 비율과 순서를 실제 사용자에 가깝게 구성한다.

### 예상 병목

- `GET /api/diaries`: 날짜 범위·정렬 쿼리의 복합 인덱스 필요성
- `POST /api/auth/login`: BCrypt 비밀번호 검증으로 인한 CPU 사용과 지연
- 일기·Refresh Token 저장: DB 커넥션 풀 포화
- JPA 연관관계 접근: N+1 쿼리 가능성

이 목록은 결론이 아니라 **측정 전에 세우는 가설**이다. k6 결과와 메트릭·로그·DB 실행 계획으로 검증해야 한다.

### 초기 성능 목표 예시

아래 수치는 학습용 출발점이며 절대적인 표준이 아니다. 실제 사용자 기대·트래픽·인프라 비용에 맞게 바꿔야 한다.

```text
일기 조회 p95 < 500ms
전체 HTTP 요청 실패율 < 1%
핵심 응답 상태 검증 성공률 > 99%
```

## 실습 내용

5단원은 이론과 설계 중심이다. 실제 부하는 6단원에서 주고, 이 단원에서는 다음을 먼저 정한다.

1. **목적**: 정상 부하를 검증할지, 한계를 찾을지 정한다.
2. **대상**: 사용자 여정과 핵심 API를 정한다.
3. **부하 모델**: VU, Ramp-up, 유지 시간, Think Time을 정한다.
4. **성공 기준**: p95, 오류율, Check 성공률을 정한다.
5. **가설**: 먼저 포화될 자원과 API를 예상한다.
6. **기록 방식**: 실행 환경과 Before/After 결과를 남긴다.

성능 테스트 계획은 최소한 다음 질문에 답해야 한다.

```text
무엇을 확인하나?
어떤 환경에서 실행하나?
얼마의 사용자가 어떤 행동을 하나?
어느 수치를 통과와 실패로 보나?
어떤 메트릭과 로그로 원인을 찾을 것인가?
```

## 실행 및 검증

성능 테스트 전에 애플리케이션이 정상적인지 헬스체크로 확인한다.

```bash
curl http://localhost:8080/actuator/health
```

예상 응답:

```json
{
  "status": "UP"
}
```

헬스체크가 실패하면 부하 테스트를 시작하지 않는다. 애플리케이션 기동·DB 연결·포트·테스트 계정을 먼저 확인한다.

부하 테스트 결과를 비교하려면 실행마다 다음 조건을 같게 유지한다.

- 애플리케이션·JDK·DB 버전
- 서버·DB·부하 발생기의 사양
- 네트워크 위치
- 테스트 데이터의 양
- VU·실행 시간·Think Time
- 캐시·JVM 워밍업 여부

이 조건이 다르면 코드 개선 효과와 환경 차이를 구분하기 어렵다.

## 문제와 해결

### VU를 늘렸는데 TPS가 비례해서 늘지 않는다

응답 시간, Think Time, DB 커넥션, Thread Pool 등에 의해 TPS가 결정된다. VU와 TPS는 같은 숫자가 아니다. TPS가 멈추고 p95만 증가하면 포화점에 가까울 수 있다.

### 평균 응답 시간은 좋은데 느리다는 문제가 있다

평균만 보지 말고 p50·p95·p99와 최댓값을 함께 확인한다. 일부 사용자만 겪는 Long Tail 지연은 평균에서 잘 보이지 않을 수 있다.

### 응답 시간이 느리면 바로 서버 사양을 높여야 하나?

먼저 병목을 측정한다. Slow Query, N+1, 커넥션 풀, Thread Pool, GC, 외부 API, 네트워크 중 어느 자원이 포화됐는지 확인한 뒤 수정한다. 사양 증가는 병목을 숨기기만 할 수 있다.

### 최대 VU를 바로 주어도 되나?

Ramp-up 없이 큰 부하를 즉시 주면 애플리케이션 워밍업·DB 커넥션 설정·캐시 생성이 한번에 겹쳐 실제 트래픽과 다른 결과가 나온다. Smoke로 확인한 후 점진적으로 올린다.

### 로컬 노트북의 결과를 운영 성능으로 봐도 되나?

로컬 결과는 스크립트 검증과 변경 전·후 비교에 유용하지만 운영 용량을 직접 의미하지 않는다. 운영과 가까운 인프라·네트워크·데이터 규모에서 다시 측정해야 한다.

### 운영 서버에 바로 부하를 주어도 되나?

실제 사용자와 데이터에 피해를 줄 수 있다. 승인된 스테이징 환경과 격리된 테스트 계정·데이터를 기본으로 사용한다. 운영 테스트가 필요하다면 영향 범위·시간·중단 기준을 사전에 합의해야 한다.

## 정리

- 성능 테스트는 빠르기·처리량·안정성·한계를 숫자로 검증한다.
- 먼저 목적을 정하고 Smoke·Load·Stress·Spike·Soak 중 적합한 테스트를 선택한다.
- VU는 가상 사용자 수, TPS는 초당 처리량이며 두 값은 같지 않다.
- 평균만 보지 말고 p50·p95·p99로 응답 시간 분포를 본다.
- SLI는 측정값, SLO는 내부 목표, SLA는 고객과의 약속이다.
- TPS가 더 이상 늘지 않고 p95·오류율만 올라가면 포화점을 의심한다.
- 실제 사용자 여정, Ramp-up, Think Time, Threshold를 포함한 시나리오를 설계한다.
- 부하 결과와 같은 시각의 메트릭·로그를 함께 봐야 병목 원인을 찾을 수 있다.
- 다음 단원에서는 k6로 이 설계를 실제 부하 스크립트로 바꾼다.
