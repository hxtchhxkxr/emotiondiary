# 01. 테스트 개요와 개발 패러다임

## 학습 목표

- 테스트가 필요한 이유를 설명할 수 있다.
- 단위·통합·E2E 테스트의 차이를 구분할 수 있다.
- TDD·BDD·DDD가 각각 어떤 질문에 답하는지 이해한다.
- emotiondiary 프로젝트에 어떤 테스트가 필요한지 판단할 수 있다.

## 핵심 개념

### 테스트란?

테스트는 코드가 **우리가 예상한 대로 동작하는지 확인하는 과정**이다.

단순히 “지금 실행된다”를 보여주는 것에서 끝나지 않는다. 코드를 수정한 뒤 기존 기능이 깨졌는지 빠르게 알려주는 **안전망** 역할을 한다.

예를 들어 일기 수정 기능을 바꿘을 때 다음과 같은 문제를 즉시 찾을 수 있다.

- 작성자 본인이 아닌데도 수정되는가?
- 내용이 2,000자를 초과해도 저장되는가?
- 수정하지 않은 날짜와 감정 값이 바뀌었는가?

### 테스트가 주는 이점

- **버그 조기 발견**: 운영에 배포하기 전에 문제를 찾는다.
- **안전한 리팩터링**: 구조를 바꿔도 기존 기능이 유지되는지 확인할 수 있다.
- **살아 있는 문서**: 테스트 이름과 코드가 기능의 사용 예시가 된다.
- **설계 개선**: 테스트하기 너무 어려운 코드는 역할이 잘 분리되지 않았다는 신호일 수 있다.
- **배포 신뢰도**: CI에서 테스트를 자동 실행하여 문제 있는 코드의 배포를 막을 수 있다.

### QA 테스트와 개발자 테스트

| 구분 | QA 테스트 | 개발자 테스트 |
| --- | --- | --- |
| 관점 | 사용자 관점 | 코드와 구조 관점 |
| 방식 | 시나리오·탐색적·수동 테스트 | 단위·통합 자동화 테스트 |
| 실행 시점 | 주로 릴리스 전 | 커밋·PR·배포 전 |
| 대표 도구 | Postman, 수동 체크리스트 | JUnit, Mockito, MockMvc, k6 |

둘 중 하나만 필요한 것이 아니다. 개발자 테스트는 반복 가능한 문제를 빠르게 찾고, QA 테스트는 실제 사용자 흐름에서 놓친 문제를 찾는다.

### 테스트의 범위

#### 1. 단위 테스트

메서드나 클래스 하나와 같은 작은 단위를 검증한다. DB·네트워크 같은 외부 의존성은 제거하거나 가짜 객체로 대체한다. 빠르고 실패 원인을 찾기 쉽다.

> 예: `DiaryService`의 특정 로직, `Diary`의 감정 범위 규칙 검증

#### 2. 통합 테스트

Controller·Service·Repository 등 여러 부분이 함께 올바르게 동작하는지 검증한다. Spring Context나 테스트용 DB를 사용하므로 단위 테스트보다 느리다.

> 예: 회원가입 요청이 Controller를 거쳐 DB에 저장되는지 검증

#### 3. E2E 테스트

실제 배포 환경에 가까운 전체 시스템을 사용자 관점에서 검증한다. 가장 실제적이지만 느리고 환경의 영향을 많이 받는다.

> 예: 회원가입 → 로그인 → 일기 작성 → 목록 조회 전체 흐름 검증

#### 4. 인수 테스트

기술적 구현보다 비즈니스 요구사항을 충족했는지 확인한다.

> 예: “로그인한 사용자는 자신의 일기만 수정할 수 있다.”

### 테스트 피라미드

테스트는 일반적으로 다음과 같은 피라미드 구조를 지향한다.

```text
           E2E 테스트        적게·느림·넓은 범위
        통합 테스트
     단위 테스트          많게·빠름·작은 범위
```

피라미드 위로 갈수록 테스트는 실제 환경에 가까워지지만 느려지고 실패 원인을 찾기 어려워진다. 따라서 **단위 테스트를 충분히 작성하고, 통합·E2E 테스트는 핵심 흐름에 집중**하는 것이 좋다.

### TDD·BDD·DDD

#### TDD: 어떻게 안전하게 만들 것인가?

TDD(Test-Driven Development)는 테스트를 먼저 작성하고 구현을 발전시키는 방식이다.

1. **Red**: 실패하는 테스트를 먼저 작성한다.
2. **Green**: 테스트를 통과하는 최소한의 코드를 작성한다.
3. **Refactor**: 테스트가 통과하는 상태에서 중복과 구조를 개선한다.

TDD의 핵심은 “무조건 테스트를 먼저 쓰기”보다 **작은 단위로 실패와 성공을 반복하는 빠른 피드백**에 있다.

#### BDD: 어떤 행동을 해야 완성인가?

BDD(Behavior-Driven Development)는 시스템의 행동을 사용자와 비즈니스 관점에서 표현한다. 보통 **Given-When-Then** 구조를 사용한다.

- **Given**: 준비된 상황
- **When**: 실행하는 행동
- **Then**: 예상하는 결과

```java
@Test
@DisplayName("로그인한 사용자가 일기를 작성하면 저장된다")
void createDiary_success() {
    // Given: 로그인한 사용자와 일기 요청이 있다.

    // When: 일기를 작성한다.

    // Then: 작성한 내용이 저장된다.
}
```

#### DDD: 무엇을 만들 것인가?

DDD(Domain-Driven Design)는 기술보다 **비즈니스 도메인과 규칙**을 중심에 두는 설계 방식이다. 일기, 사용자, 감정, 작성자 같은 도메인 언어를 코드와 테스트에서 일관되게 사용한다.

핵심 도메인 규칙은 가능하면 Service 곳곳에 흩어놓지 말고 해당 도메인 객체에 표현한다. 그러면 DB 없이도 빠르게 규칙을 테스트할 수 있다.

#### 세 개념의 관계

- **DDD**: 무엇을 만들지 정한다.
- **BDD**: 어떤 행동이 완성 조건인지 정한다.
- **TDD**: 이를 어떻게 안전하게 구현할지 이끈다.

세 방법은 경쟁 관계가 아니며, 프로젝트 복잡도와 팀의 필요에 따라 함께 또는 부분적으로 사용한다.

## 프로젝트 적용

emotiondiary에서는 테스트 범위에 따라 다음과 같이 역할을 나눈다.

| 검증 대상 | 테스트 범위 | 예시 |
| --- | --- | --- |
| Diary 필드와 도메인 규칙 | 단위 테스트 | 감정 ID의 유효 범위 검증 |
| DiaryService 로직 | 단위 테스트 + Mock | 저장·조회·삭제 로직 검증 |
| DiaryController HTTP 계약 | 슬라이스 테스트 | 요청 검증, 상태 코드, JSON 응답 검증 |
| DiaryRepository JPA 쿼리 | 통합 테스트 | 사용자·날짜 조건의 조회 결과 검증 |
| 회원가입·로그인 전체 흐름 | 통합/E2E 테스트 | 실제 요청과 응답, DB 저장 검증 |
| 동시 사용자 부하 | 성능 테스트 | k6로 TPS·p95·오류율 측정 |

핵심은 **모든 것을 통합 테스트로 확인하지 않는 것**이다. 간단한 계산과 규칙은 빠른 단위 테스트로, Spring 설정·JPA·HTTP 연동은 필요한 범위의 통합 테스트로 확인한다.

## 실습 내용

이 단원은 특정 도구를 다루기보다 이후 실습의 기준을 잡는 단원이다.

1. 기능의 핵심 요구사항을 테스트 이름으로 표현한다.
2. 각 요구사항에 단위·통합·E2E 중 어느 범위가 적합한지 고른다.
3. Given-When-Then으로 상황·행동·결과를 나누어 생각한다.
4. 실패하는 테스트를 먼저 작성하고 최소 구현으로 통과시키는 TDD 흐름을 이해한다.

예시 요구사항은 다음과 같이 나눌 수 있다.

```text
요구사항: 사용자는 자신의 일기만 삭제할 수 있다.

Given: 사용자 A와 사용자 B의 일기가 저장되어 있다.
When:  사용자 A가 사용자 B의 일기 삭제를 요청한다.
Then:  삭제가 거부되고 기존 일기는 유지된다.
```

## 실행 및 검증

1단원은 개념 중심이므로 새로운 테스트 코드를 실행하지 않는다. 이후 단원에서 작성한 전체 테스트는 프로젝트 루트에서 다음 명령으로 확인한다.

```bash
./gradlew test
```

좋은 테스트는 다음 질문에 대부분 “예”라고 답할 수 있어야 한다.

- 테스트 이름만 보고 검증하는 행동을 알 수 있는가?
- 다른 테스트와 실행 순서에 의존하지 않는가?
- 실패했을 때 원인을 빠르게 찾을 수 있는가?
- 구현 세부사항이 아니라 중요한 행동을 검증하는가?

## 문제와 해결

### 테스트가 많으면 무조건 좋은가?

아니다. 중복되거나 구현 세부사항에 과도하게 의존하는 테스트는 유지보수 비용만 높인다. **핵심 규칙·오류 경계·사용자 흐름**을 우선해야 한다.

### 통합 테스트만 작성하면 되지 않나?

통합 테스트는 신뢰도가 높지만 느리고 실패 원인을 찾기 어렵다. 단순한 규칙은 단위 테스트로 빠르게 검증하고, 실제 연동이 중요한 부분만 통합 테스트로 남긴다.

### TDD는 반드시 모든 코드에 적용해야 하나?

그렇지 않다. 요구사항이 명확하고 규칙이 중요한 로직에 특히 유용하다. 빠른 시도가 필요한 프로토타입이나 단순 설정 코드에는 비용이 더 클 수 있다.

### 테스트하기 어려운 코드는 어떻게 해야 하나?

클래스가 너무 많은 역할을 담고 있거나 DB·시간·네트워크 같은 외부 요소와 강하게 결합되었는지 확인한다. 역할을 나누고 외부 의존성을 주입받도록 개선하면 테스트하기 쉬워진다.

## 정리

- 테스트는 버그를 찾는 것을 넘어 **변경을 안전하게 만드는 장치**이다.
- 단위 테스트는 작고 빠르며, 통합·E2E 테스트는 넓은 범위를 검증하지만 더 느리다.
- 단위 테스트를 충분히 작성하고 통합·E2E 테스트는 핵심 흐름에 집중한다.
- DDD는 **무엇**, BDD는 **어떤 행동**, TDD는 **어떻게 안전하게**에 초점을 맞춘다.
